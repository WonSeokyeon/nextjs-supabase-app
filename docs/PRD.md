# PRD: 모임 이벤트 관리 웹 MVP

## 1. 배경 및 문제 정의

수영, 헬스, 친구 모임 등 정기적으로 모이는 소모임에서 주최자는 다음 업무를 반복적으로, 대부분 수작업(카카오톡 단체방, 엑셀, 개인 메모)으로 처리한다.

- **공지**: 모임 일정/장소 변경, 준비물 등을 매번 공지해야 함
- **참여자 관리**: 누가 오는지/안 오는지 파악, 정원 관리
- **카풀**: 누가 태워줄 수 있는지, 누가 탑승이 필요한지 매칭
- **정산**: 대관료·간식비 등 공동 비용을 걷고 입금 여부를 확인

이 네 가지 업무가 채팅방 대화 속에 흩어져 있어 주최자의 반복 노동이 크고, 참여자 입장에서도 정보를 놓치기 쉽다. 이 프로덕트는 이 업무를 한 곳에서 처리할 수 있는 웹 도구를 제공해 주최자의 운영 부담을 줄이는 것을 목표로 한다.

## 2. 목표

- 모임 주최자가 클럽(정기 모임)과 회차(이벤트)를 만들고, 공지·참여자·카풀·정산을 한 화면 흐름 안에서 관리할 수 있게 한다.
- 참여자는 초대코드로 클럽에 가입하고, 회차별로 참석 여부를 답하고, 카풀/정산 현황을 확인할 수 있게 한다.
- 실제 결제 연동 없이도 "누가 얼마를 냈고 누가 얼마를 내야 하는지"를 투명하게 계산·기록해 주최자의 정산 부담을 줄인다.

## 3. 대상 사용자

| 역할               | 설명                                                                  |
| ------------------ | --------------------------------------------------------------------- |
| 주최자 (owner)     | 클럽을 만들고 전체를 운영. 클럽/이벤트/공지/정산 최종 관리 권한       |
| 운영진 (admin)     | 주최자가 위임한 보조 관리자. 이벤트/공지/멤버 관리 가능 (설정은 제외) |
| 일반 멤버 (member) | 초대코드로 가입, RSVP, 카풀 신청, 정산 현황 열람                      |

## 4. 범위

### 4.1 MVP에 포함되는 기능

1. **클럽 & 멤버십** — 클럽 생성, 초대코드 발급/재발급, 초대코드로 가입, 역할(owner/admin/member) 관리, 탈퇴/추방
2. **이벤트(회차) & 참여자 관리** — 클럽 아래 회차 생성, 정원 설정, RSVP(참석/불참/대기/미정), 정원 초과 시 대기 처리
3. **공지** — 클럽 단위 또는 특정 회차 단위 공지 작성, 상단 고정
4. **카풀** — 운전자가 좌석 제공(출발지/시간/좌석수) 등록, 참여자가 탑승 신청, 운전자가 승인/거절
5. **정산** — 회차별 비용 항목 등록(누가 얼마를 냈는지), 참석자 기준 자동 분담 계산, 주최자가 입금 확인 체크

### 4.2 MVP에서 제외되는 기능 (명시적 비목표)

- 실제 결제(PG) 연동 — 정산은 계산/기록만, 송금은 카카오페이 등으로 참여자가 외부에서 직접 처리
- 클럽 공개 탐색/검색 — 가입은 초대코드로만 가능 (비공개 모임 전제)
- 알림 (이메일/푸시/카카오 알림톡)
- 대기자 자동 승급 (주최자가 수동으로 승급 처리)
- 반복 이벤트 자동 생성 (매주 반복 등 RRULE 기반 자동화)
- 지도 기반 위치 선택 (텍스트/링크로 장소 표기)

이 항목들은 MVP 이후 우선순위에 따라 재검토한다.

## 5. 핵심 사용자 흐름

**주최자**: 클럽 생성 → 초대코드 공유 → 회차(이벤트) 생성 → 공지 작성 → 참석 현황 확인 → (필요 시) 카풀 매칭 승인 → 회차 종료 후 비용 항목 입력 → 참여자별 입금 확인 체크

**참여자**: 초대코드로 클럽 가입 → 회차 목록에서 RSVP → (차량 필요 시) 카풀 탑승 신청 → 정산 화면에서 본인 분담액 확인 → 외부(카카오페이 등)로 송금

## 6. 데이터 모델 개요

클럽(clubs) 아래에 멤버십(club_members), 회차(events)가 있고, 회차 아래에 참여자(event_participants), 공지(announcements, 클럽 단위도 가능), 카풀(carpool_offers/carpool_requests), 정산(settlements/settlement_items/settlement_shares)이 종속된다.

- **정산 분리 원칙**: `settlement_items`(누가 얼마를 "냈는지")와 `settlement_shares`(누가 얼마를 "내야 하는지" + 입금 확인 여부)를 분리해, 계산과 확인 상태를 독립적으로 관리한다.
- **권한 원칙**: 조회는 클럽 멤버 전체, 대부분의 쓰기(공지/이벤트/정산)는 owner/admin, RSVP·카풀 신청 등 본인 관련 행위는 본인이 수행.

상세 테이블 스키마 및 RLS 설계, 화면/라우트 구조, 단계별 구현 순서는 `.claude/plans/snazzy-exploring-mango.md` 구현 계획 문서를 따른다.

## 7. 성공 기준 (MVP 검증 관점)

- 주최자가 클럽 생성부터 정산 마감까지 전체 흐름을 채팅방 없이 이 서비스만으로 완결할 수 있는가
- 참여자가 초대코드 가입 → RSVP → 정산 확인까지 별도 안내 없이 직관적으로 수행할 수 있는가
- 정산 화면에서 "누가 얼마를 내야 하는지"와 "누가 입금했는지"가 한눈에 구분되는가

## 8. 기술 스택 / 제약

- Next.js 16 (App Router) + Supabase Auth(SSR 쿠키 기반), `cacheComponents: true`
- 신규 스키마는 Supabase MCP(`apply_migration`)로 원격에 직접 적용 (로컬 마이그레이션 CLI 없음)
- 기존 인증 폼(useState 기반)은 유지, 신규 모임 관련 폼에 한해 React Hook Form + Zod 도입
- 상세 기술 설계는 `.claude/plans/snazzy-exploring-mango.md` 참고
